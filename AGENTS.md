# Pods — project rules

## Security model (non-negotiable)

This project treats npm supply-chain compromise as the primary threat. The development boundary is a hardware-isolated VM via Apple's `container` CLI.

1. **NEVER run `npm`, `npx`, or `node` on the host.** All client toolchain execution goes through the dev container: `container exec pods-dev <cmd>` (helpers in `dev/`).
2. **NEVER mount `.git` or the repo root into the container.** Only `client/` is mounted. A guest-writable `.git` enables host code execution via hooks/`core.fsmonitor`/smudge filters.
3. Git runs on the host only. The guest holds no GitHub/SSH credentials.
4. `node_modules/` lives in a guest-only volume — untrusted packages never land on host disk.
5. npm runs with `ignore-scripts=true` and `save-exact=true` (enforced by `client/.npmrc`). Lockfiles are committed.
6. Podcast Index credentials stay in the host-only credential store: `~/.config/podcasts/credentials.env`. The Mac backend reads them. Never include credentials in the browser build.

## Dev workflow

- After every turn, commit that turn's work on `main` and push it to `origin/main`.
- After a turn that changes the Mac backend (`backend/` or the `mac/backend/` runtime the installed service runs), install that backend in the same turn. Do not wait to be asked. From the repo root run `python3 mac/backend/manage.py install`, then `launchctl kickstart -k gui/$(id -u)/dev.mcgiv.pods-backend`. Install builds the release binary, rebuilds the client in `pods-dev`, and atomically retargets `~/.local/share/pods/current`. The running service resolves `current` once at start, so the kickstart is what loads the new binary. If `pods-dev` is down, install a backend-only release instead: copy the live `current` tree into `releases/<YYYYMMDD-HHMMSS>`, replace `pods-backend` (and `runtime/manage.py` when it changed), retarget `current` the way `install()` does (write `current.next` as a symlink, then `Path.replace` it onto `current`), then kickstart. Do not `mv` or `ln` onto `current` while the shell is following that symlink. A client-only or docs-only turn does not reinstall the backend. Client production deploy stays the Cloudflare Pages steps below.
- `dev/up.sh` — build the image and start the long-lived `pods-dev` container (mounts, ports, resources).
- `dev/sh.sh [cmd...]` — exec into the container (interactive shell if no args).
- `dev/check.sh` — the merge gate: frontend Vitest coverage (≥90% lines, statements, and functions, enforced in `vite.config.ts`).
- Vite dev server: `:5173`.
- Client production deploy: **Deploy the client** in `docs/mac-backend.md`. Build in `pods-dev`, zip `client/dist/` at the zip root, then upload that zip with local Chrome through browser-harness in the Cloudflare Pages dashboard. Do not use Wrangler, `npx`, GitHub Actions, or `infra/deploy.sh`. Do not create a new Pages project or change DNS.

## Menu bar app

The Mac menu-bar app is Pods Pipeline Preview (`Pods Speaker`, `dev.mcgiv.pods.speaker`). `~/Applications/Pods Pipeline Preview.app` is a symlink to `/Applications/Pods Pipeline Preview.app`.

- The next build has to replace the app in `/Applications`. Copying a new bundle onto the `~/Applications` path would replace the link, and `mbm` would hide the icon again. MenuBarAgent does not attribute a status item whose real path is outside `/Applications`, and `mbm` hides every unattributed icon while it is running.
- After replacing the bundle, relaunch it from `/Applications`. Login agent `dev.mcgiv.pods-speaker` runs `open -W "/Applications/Pods Pipeline Preview.app"`.

## Default app/runtime

- The browser at `pods.mcgiv.dev` is the supported client. The first native iOS app was removed on 19 October 2026; its source is in git history.
- A native iPhone app lives in `ios/` (rebuilt from 13 November 2026). It is 100% native SwiftUI and AVFoundation: no `WKWebView`, no web content, no third-party packages, no on-device backend, no FFI. It speaks the same sync protocol as the browser (`GET /api/sync`, `POST /api/sync/actions`, ranged `GET /api/artifacts/<hash>` with per-chunk SHA-256 checks) and keeps the library, an outbox, and downloaded media in `Application Support/Pods`. Do not restore the old `ios/` tree, `backend/src/ffi.rs`, or the old refresh scripts. On 18 November 2026 it passed its unit and UI tests in the Simulator and was installed on Matt's iPhone, where it paired, synced, downloaded, and played.
- The native app pulls the library with `GET /api/sync?version=2`: the same snapshot, except that played and archived episodes are summaries (`"summary": true`, empty `notes_html` and `show_notes`, `manifest.chunks: []`). That is about 0.8 MB instead of 5.3 MB, and about 180 KB after the proxy's compression. Version 1 (the browser's) is unchanged; keep both. `GET /api/episodes/<id>/detail` returns one episode's full record; the app fetches it to play or download a summarized episode, fills in only the notes, chapters and chunk hashes (and only for the same file, so newer play state wins), and keeps that detail (marked `local_detail`) through later pulls while the file is unchanged; other finished episodes shrink to summaries. If the detail is for another file, it pulls and tries once more. It pulls again after marking a summarized episode unplayed. It pulls at launch, on pull-to-refresh, and at most every 30 minutes; between those it reads `revision` from `GET /api/status` and pulls only when it differs from the snapshot's `cursor`. Keep the snapshot `cursor` equal to `browser_clock.revision`, and bump that revision for any change the clients must see.
- The proxy compresses responses (`encode zstd gzip` in the Caddyfile that `manage.py` writes). Audio is not compressed.
- Downloads use a background `URLSession` (`dev.mcgiv.pods.media`), so they continue while iOS suspends or ends the app; a force-quit from the app switcher cancels them until the app is opened again. Each transfer is an 8 MiB range (8 chunks; the Mac reads each range into memory, so do not request whole files). Every chunk is checked against the manifest before it is written at its offset in `<hash>.part`; `<hash>.json` records finished segments, and the file is renamed to `<hash>.<m4a|mp4>` only when all are in. iOS runs transfers queued while the app is in the background only when it chooses (usually Wi-Fi and power), so the app queues the whole plan while it is on screen (one segment per 8 MiB of the storage limit plus one per episode, 306 at the defaults, at most 512) and orders it by task priority: high for the next episode, default for the one after, low for the rest, updated on queued transfers whenever the order changes. Episodes downloaded by hand are saved in user defaults with their played state at the time, and they and their files stay until that state changes (played or archived), so their transfers survive iOS ending the app; their segments are added to the queue size, on top of the 512 cap (up to another 512). The queue is re-planned when Listen, those requests or the download settings change (not on position saves), after each finished segment, and every minute. When the Mac fails outright (a transfer or sync gets a 5xx, a refused or lost connection, or 401/403), nothing new is queued for 30 s, doubling up to 30 min; failures that arrive while the wait runs do not lengthen it, any failure after it counts as a failed probe, and transfers already queued are left to finish or fail. After the wait one segment goes out as a probe, and the next stored segment ends the backoff. The first sync that reaches the Mac after a failed one (it is back, or the iPhone paired again) and a tap on Download end the wait at once (the probe goes out). Nothing is queued while the iPhone is known to be unpaired. Each transfer records whether it was queued with the app on screen; when the app is on screen, transfers queued in the background that have not started are cancelled and queued again, since iOS runs those only when it chooses. Sync pulls (`GET /api/sync`) re-send the session cookie with a fresh 30-day `Max-Age`, so a device in use never has to pair again. Partial-file state carries a generation, is discarded when it claims more than the partial file holds, and never replaces a finished file. The app also asks iOS for background refresh (`dev.mcgiv.pods.refresh`, `.backgroundTask(.appRefresh)`), which syncs, queues downloads, renews reminders and reports to the Mac. iOS decides when that runs; the Simulator cannot run it.
- Reminders: the app schedules local notifications 36 and 6 hours before its signature runs out, and Listen shows a banner in the last two days. They are rebuilt from the installed profile on every launch, foreground and background refresh, so a reminder can still fire after a re-sign if the app has not run since.
- Device reports: the app sends its status and the last 64 KB of its log with `PUT /api/devices/<client_id>/report` at launch, every 30 minutes, on going to the background and on background refresh. The Mac keeps the latest per device in `<data root>/Diagnostics/devices/<client_id>.json` (session required; only client IDs that have synced; 256 KB limit). `pods-ios.py status` prints the newest one from a real iPhone (reports carry `"simulator": true|false`), so the phone's state is visible without a cable. UI tests in read-only mode send no reports.
- The app identifies itself with `User-Agent: Pods-iOS/<version> (<build>; iOS <version>)` and `x-pods-client: ios`, and sends no `Origin`. The backend rejects a mismatched `Origin` and accepts requests without one.
- Shared sync vectors: `client/src/offline/sync-vectors.json` holds the timeline, overlay, outbox and snapshot-validation cases every client must agree on. `backend/tests/sync_vectors.rs` (timeline), `ios/PodsTests/SyncVectorTests.swift` (all) and `client/src/offline/syncVectors.test.ts` (timeline, overlay, outbox and the version 1 validation cases) read it. Change a rule there first, then make each client pass.
- Behavior rules that the browser client follows (sync conflict handling, position mapping through the manifest timeline, download limits, no discovery) apply to the native app too. When one changes, change both clients. `ios/Pods/SyncLogic.swift` mirrors the browser's sync rules.
- Native sign-in is a pairing code, because a free Personal Team cannot use passkeys (no Associated Domains). `python3 mac/backend/manage.py pair` prints a single-use code valid for ten minutes (only its hash is stored, in `auth_pair_tokens`); `POST /api/auth/pair` exchanges it for the normal `pods_session` cookie. Anyone who can run commands as Matt on this Mac can mint a session this way; that is the same trust boundary as `manage.py enroll`. The app sends no `Origin` (see its identity below).
- The app is signed with a free Personal Team (seven-day signatures). Only Xcode on this Mac signs and installs it: no third-party sideloading tools, no paid developer account. `ios/tools/pods-ios.py` does it (`install`, `refresh`, `status`, `schedule`); team ID and device ID live in `~/.config/podcasts/ios.env`, never in the repo. The refresh reuses compiled output, treats "installed" as success, and never launches the app. It still needs this Mac awake and the iPhone reachable at least once inside the last three days of each signature.
- iOS tests: `cd ios && xcodebuild -project Pods.xcodeproj -scheme Pods -destination "platform=iOS Simulator,name=iPhone 17 Pro" -derivedDataPath build/DerivedData test`. `PodsTests` covers the pure sync rules, the shared vectors, segment storage and verification, reminders, and car rules; `PodsUITests` drives the real app against the live Mac library. UI tests must launch the app with `-PodsReadOnly YES` (they do): in that mode local changes stay in memory and are never sent, so tests cannot change Matt's library. Never remove that argument or add a UI test that runs without it. If the Simulator app is unpaired, pass `TEST_RUNNER_PODS_PAIR_CODE="$(python3 mac/backend/manage.py pair)"`.
- Test targets are built only for the test action, never for `build`, so device installs do not register extra App IDs (a free team gets 10 per week).
- Not in the native app yet: Mac speaker output, voice feedback, OPML import, video picture, processing notifications and pipeline views. Use the browser for those.
- As of 18 November 2026 the `pods-dev` container has no outbound network (even to an IP address), probably because of the Mullvad exit node, which must stay enabled. `npm` cannot install there, so client checks, builds and deploys cannot run. `client/src/offline/syncVectors.test.ts` and the small `client.ts` refactor that exports `coalesceOutbox`, `nextBatch`, `originalTime` and `processedTime` for it have not run yet; run `dev/check.sh` first once the container is reachable. Until then, install backend-only releases: build with cargo, copy the current release to a new `releases/<timestamp>`, replace `pods-backend` and `runtime/manage.py`, switch `current`, and `launchctl kickstart -k gui/$(id -u)/dev.mcgiv.pods-backend`.
- The library/API backend is the Rust crate in `backend/` (`Backend::handle`), hosted on the Mac. The browser must work from downloaded data while the Mac is unavailable.
- The browser synchronizes over HTTPS through Tailscale while the Mac is awake and connected. Only processed episodes with finished show notes are published.
- For user-facing library/API behavior, implement backend changes in Rust (`backend/`) and cover them with `cargo test`.
- The iPhone client app (Swift), the in-app iPhone "backend" (loopback server + Rust FFI shell), and all iPhone signing/install tooling were removed on 19 October 2026 after the 1 October deprecation. The old tree lived in `ios/` (deleted) plus `backend/src/ffi.rs`, `backend/include/pods_backend.h`, and `backend/build-ios.sh` (all deleted). Historical records of that work remain in dated docs such as `ios/DEPRECATED.md` via git history.
- There is no active Hetzner remote dev host for this project.
- There is no Vultr VPS. Cloudflare Pages serves the client. The Mac host runs the backend.

## Product rules

- Personal mobile client for iPhone and iPad, including portrait, landscape, and split-screen widths.
- Primary browser: **Chrome on iPhone** — Matt uses it most of the time. Pods is for his personal use, so optimize for Chrome's features. (Note: Chrome on iOS still uses the WebKit engine, so web-platform capabilities match Safari; the differences are in browser UI/features, not the rendering/JS engine.)
- **No discovery/recommendation features — ever.** This is an anti-requirement from Matt.
- Recent (default view) = unplayed episodes, oldest first. Mark-played removes; Played view is the archive.
- Client runtime deps stay at exactly `react` + `react-dom`. Routing is the hand-rolled hash router in `client/src/router.ts`. Justify any proposed new dependency in terms of the supply-chain posture.
- App display name: `APP_NAME` in `client/src/config.ts` + `client/public/manifest.webmanifest`.
